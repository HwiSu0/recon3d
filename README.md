# 통로 3D 복원

불투명한 상자 속 호스에 철 현탁액을 흘리고, 바깥 자기장 센서 4대의 측정값으로 호스가 지나간 길을 3차원으로 복원하고 호스 내경을 추정하는 웹 프로그램입니다.

설치할 것이 없습니다. 페이지를 열고 Capstone CSV를 넣으면 브라우저 안에서 계산하고, 돌려 볼 수 있는 3D 결과를 보여 줍니다. 측정 파일은 서버로 전송되지 않습니다.

페이지 주소: <https://hwisu0.github.io/recon3d/>

## 사용법

1. **측정 파일**: Capstone에서 File > Export Data > Export to file로 저장한 CSV를 넣습니다. 여러 Run이 든 파일도 됩니다.
2. **실험 조건**: 기존 설정을 고르거나 설정 JSON을 연 뒤 이번 Run에 맞게 고칩니다. 내경까지 구하려면 출구별 유량도 넣습니다.
3. **복원 시작**을 누릅니다. 끝나면 3D 결과가 오른쪽에 나타나고, HTML과 JSON으로 저장할 수 있습니다.

복원한 결과는 자동으로 **결과** 탭에 쌓이고, 누르면 다시 볼 수 있습니다. 결과는 쓰고 있는 브라우저 안에만 저장되어 다른 컴퓨터나 팀원에게는 보이지 않고, 브라우저 데이터를 지우면 사라집니다. 다른 컴퓨터로 옮길 때는 **HTML 저장**으로 받은 파일을 그쪽에서 **결과 HTML 가져오기**로 넣습니다.

처음 실행할 때는 파이썬 실행 환경 약 35 MB를 내려받습니다. 페이지를 열면 바로 준비를 시작하고, 다음부터는 브라우저에 저장된 것을 씁니다.

CPU 코어 2개 시험 환경에서 준비가 끝난 뒤 복원 시작부터 결과까지 걸린 시간입니다. 코어가 많으면 워커 4개까지 나눠 계산합니다.

| 데이터 | 시간 |
| --- | --- |
| Run #40, 구조 고정 | 약 2초 |
| Run #49, 구조 고정 | 약 12초 |
| 가상 Run #54, 구조와 출구 자동, 단순한 구조로 끝남 | 약 4초 |

### 구조 고르기

`topology`가 `auto`면 후보 구조를 모두 맞춰 보고 BIC가 가장 작은 것을 고릅니다. 결과의 **구조** 칸에서 후보별 점수를 비교할 수 있습니다.

보통의 BIC는 잔차가 서로 독립인 잡음이라고 봅니다. 실측에는 앞머리 모델로 설명되지 않는 신호가 시간에 따라 이어져 남아서 $\chi^2$ 차이가 부풀려지고 매개변수가 많은 구조가 유리해집니다. 그래서 $\chi^2$이 가장 낮은 후보의 잔차로 이웃한 시간끼리의 상관 $\rho$를 재서 보정합니다.

$$\mathrm{BIC} = \frac{\chi^2}{c} + k \ln\frac{N}{f}, \qquad f = \frac{1+\rho}{1-\rho}, \qquad c = f \max\left(1, \frac{\chi^2_\mathrm{min}}{N}\right)$$

$k$는 매개변수 수, $N$은 자료 수입니다. 잔차가 독립인 잡음이면 $c = f = 1$이라 보통의 BIC와 같습니다. 앞선 두 후보의 차이가 10보다 작으면 결과에 경고를 표시합니다.

구조는 단순한 것부터 맞춥니다. 한 줄 관과 굵기 변화 관이 잡음 수준까지 맞아서 합류 관이 완벽하게 맞아도 BIC로 이길 수 없으면 합류 관은 맞추지 않습니다. 합류 관은 한 줄 관이 잘 맞은 출구에서만 시험합니다 (`exit_near`). 호스는 3 mm와 5 mm뿐이므로 굵기 변화 관의 굵기 비가 1.25보다 작으면 굵기 변화로 보지 않고 표에 `굵기 변화 없음`으로 표시합니다 (`step_min_ratio`).

| 값 | 구조 |
| --- | --- |
| `single` | 한 줄 관. 중간점 1개, 굵기 일정 |
| `step` | 중간에 굵기가 바뀌는 한 줄 관. 바뀌는 점 P와 앞뒤 굵기 비를 찾습니다 |
| `loop` | 갈라졌다 다시 모이는 관. 분기점 J1, 합류점 J2, 갈래마다 중간점을 찾습니다 |
| `y` | 갈래마다 다른 출구로 나가는 Y자 |

`candidates`로 후보를 줄일 수 있고, `exit`가 `auto`면 출구마다 모든 후보를 맞춥니다. `try_y`는 Y자를 후보에 넣을지 정합니다. `prior`의 `straight_sigma_cm`은 곧은 관을, `downhill`은 내리막 관을 선호하게 합니다. 후보가 많을수록 오래 걸리므로 구조나 출구를 알면 직접 정하는 편이 빠릅니다. 2단계에서 가장 좋은 후보보다 $\chi^2$이 1.5배 넘게 큰 후보는 마무리를 건너뛰고, 표에 `약`을 붙여 표시합니다.

### 경로 모양

호스는 꺾인 직선이 아니라 곡선으로 계산합니다. 입구, 중간점 C, 출구를 지나는 매끈한 3차 곡선이고, 미지수 수는 늘지 않습니다. `curve`로 고릅니다.

| 값 | 화면 | 뜻 |
| --- | --- | --- |
| `true` (기본) | 곡선, 구멍에 수직 | 호스가 구멍에서 벽에 수직으로 드나듭니다 |
| `"free"` | 곡선, 끝 방향 자유 | 끝 방향을 정하지 않습니다 |
| `false` | 꺾인 직선 | 이전 방식입니다. C에서 꺾입니다 |

평균 경로 오차(cm)입니다. 가상 호스는 복원 모델과 다른 식으로 만들었습니다.

| 호스 모양 | 꺾인 직선 | 끝 자유 곡선 | 구멍 수직 곡선 |
| --- | --- | --- | --- |
| 수직으로 나와 완만히 내려감 | 0.42 | 0.42 | 0.06 |
| 수직, 옆으로 휨 | 1.31 | 1.45 | 0.22 |
| 수직, S자 | 1.28 | 1.39 | 0.98 |
| 비스듬히 나오는 직선 | 0.03 | 0.03 | 0.54 |
| 비스듬히 나오는 휨 | 0.40 | 0.20 | 1.25 |
| 실측 Run #40 | 0.29 | 0.31 | 0.33 |

호스가 구멍에서 비스듬히 빠진다면 구멍 수직 곡선은 오히려 나빠집니다. 이때는 끝 자유 곡선을 쓰고 χ²/N을 비교하세요. 가상 호스 5가지에서는 두 곡선 중 χ²/N이 낮은 쪽이 경로 오차도 작았습니다. 실측 Run #40에서는 세 방식의 χ²/N과 경로 오차가 거의 같아서 구분되지 않습니다. 중간점이 하나뿐이라 S자처럼 복잡한 모양은 최대 오차가 3 cm 넘게 남습니다.

### 자동 선택의 한계

가상 Run #54(3 mm에서 5 mm로 굵어지는 관)에서는 굵기 변화와 뒤쪽 출구를 맞게 골랐습니다. 가상 호스가 곡선이면 굵기 바뀌는 점의 오차가 0.03 cm이고, 꺾인 직선이면 구조는 맞게 고르지만 오차가 0.38 cm로 커집니다.

실측 Run #40은 곧은 호스이고 자동 선택도 한 줄 관을 고릅니다.

실측처럼 앞머리 모델이 설명 못 하는 신호가 있을 때를 보려고 가상 데이터에 Run #40에서 맞추고 남은 신호를 더해 시험했습니다.

| 가상 호스 | 남은 신호 없음 | Run #40만큼 | 2배 |
| --- | --- | --- | --- |
| 굵기 변화, 뒤쪽 출구 | 맞음 | 맞음 | 맞음 |
| 합류 관 | 맞음 | 틀림 (굵기 변화) | 맞음 |

남은 신호가 크면 진짜 합류 관을 놓칠 수 있으므로, χ²/N이 2보다 크면 결과에 경고를 표시합니다. 실측 Run #53, #54로는 아직 확인하지 못했습니다. Run #40 기본 설정은 한 줄 관으로 고정했습니다.

좌표 (a, b, c)는 a가 입구면에서 출구 쪽, b가 앞면(S3 쪽)에서 안쪽, c가 탁자에서 높이입니다. 그 밖의 항목은 화면의 **JSON** 에서 고칩니다. 새 설정을 목록에 넣으려면 파일을 `configs/`에 두고 `configs/index.json`에 한 줄 추가합니다.

### 결과 읽는 법

- **χ²/N**: 1에 가까울수록 잡음 수준까지 맞은 것입니다. 괄호의 철 없음 값보다 많이 작아야 의미가 있습니다. **맞춘 구간** 안에서 계산한 값입니다.
- **맞춘 구간**: 앞머리가 상자를 지나는 구간입니다. 그 뒤에는 뒤따르는 철과 호스에 남은 철이 섞여 앞머리 모델로 설명되지 않아서 경로를 맞출 때 쓰지 않습니다. 아래 그래프는 전체 시간을 그리므로 이 구간 뒤에서 측정과 모델이 벌어지는 것은 정상입니다.
- **실제 경로로 맞출 때 χ²/N**: 복원 경로의 값보다 크게 높지 않아야 합니다. 틀린 경로의 χ²/N이 더 낮다면 신호가 부족해 복원을 믿을 수 없다는 뜻입니다. 실제 경로는 적힌 점을 잇는 매끈한 곡선으로 쓰며, 두 점이면 직선입니다.
- **다른 후보**: 가는 반투명 관으로 그려집니다. 후보끼리 많이 다른 곳이 불확실한 곳입니다.
- **아래 그래프**: 옅은 선이 측정, 진한 선이 모델입니다. 겹칠수록 잘 맞은 것입니다.

## 호스 내경 추정

자기장 측정만으로는 내경을 직접 알 수 없습니다. 호스가 센서에서 호스 굵기보다 훨씬 멀어서 철이 만드는 신호는 $\lambda = \chi_\mathrm{eff} A$, 즉 실효 자화율과 단면적의 곱으로만 나타나기 때문입니다. 그래서 Capstone 측정값으로 앞머리 속도 $U$를 구하고, 출구에서 잰 유량 $Q$를 더해 계산합니다.

$$d = 2\sqrt{\frac{Q}{\pi U}}$$

복원에서 고른 구조의 경로를 고정하고 구간마다 속도를 구합니다. 설정에 실제 경로가 있고 측정을 복원 경로만큼 맞추면 실제 경로를 쓰고, $\chi^2/N$이 복원 경로의 1.25배를 넘으면 복원 경로를 씁니다. `step`은 굵기가 바뀌기 전과 뒤, `y`와 `loop`는 입구 쪽과 갈래별 구간입니다. `loop`의 갈래는 갈래별 유량을 재기 어려워 신호 크기 비로만 내경을 냅니다.

속도는 첫 앞머리가 상자를 지나는 구간만 맞춰서 구합니다. 그 뒤의 신호에는 뒤따르는 덩어리와 호스에 남은 철이 섞여 있어, 전체 구간을 맞추면 Run #40의 속도가 실제의 절반 아래로 나옵니다.

속도를 바꿔 가며 맞춤이 얼마나 나빠지는지 보고, $U/2$와 $2U$ 양쪽에서 3σ 넘게 나빠지지 않거나 속도 불확도가 50%를 넘으면 **판정 불가**로 표시하고 값을 내지 않습니다. 불확도에는 맞춤 오차, 구간 길이를 바꿨을 때의 차이, 유량 오차 5%를 넣습니다.

구간이 나뉘는 호스에서 신호가 충분히 크면 농도가 같다는 가정으로 $d_k = d_\mathrm{입구} \sqrt{\lambda_k / \lambda_\mathrm{입구}}$ 도 함께 보여 줍니다. 이 값은 유량이 필요 없습니다.

곧은 호스와 Y자, 곡선 호스의 가상 데이터는 모델 자체로 만들고 측정과 같은 크기의 잡음을 넣은 것입니다. 실제 호스처럼 뒤따르는 덩어리가 없어 실측보다 쉬운 시험입니다. 꺾인 굵기 변화 관은 곡선 모델과 다른 모양을 곡선 모델로 맞춘 경우로, 경로 모양이 틀리면 굵기 바뀌기 전 내경과 신호 크기 비가 표시된 불확도를 넘어 틀릴 수 있음을 보여 줍니다.

Run #40의 검증은 잠정입니다. 유량 0.21 mL/s는 실험 기록의 값이고, 모은 양 ÷ 시간으로 직접 잰 값인지 아직 확인하지 못했습니다. 3 mm 단면적으로 계산한 값이라면 정답이 입력에 들어간 것이므로 검증이 되지 않습니다. Run #49의 출구별 유량도 기록된 모은 양 비율(12:4)로 총유량 0.21 mL/s를 나눈 값입니다.

앞머리 배율 $\gamma$($U = \gamma Q / A$)는 1로 두었습니다. 실제 값이 다르면 내경은 $\sqrt{\gamma}$배 달라지므로 곧은 호스 흐름 보정으로 따로 재야 합니다. 값까지 비교할 수 있는 실측은 Run #40 한 건뿐이어서, 다른 내경의 실측으로 더 확인해야 합니다.

Run #40에서 센서를 하나씩 빼면 S1은 2.91 mm, S2와 S3은 3.15 mm, 출구 쪽 S4는 3.80 mm가 나옵니다. 앞머리가 통과하는 시간을 재려면 출구 가까이에 센서가 꼭 있어야 합니다. 표시되는 불확도에는 이 센서 배치 영향이 들어 있지 않습니다.

## 작동 방식

```
index.html, assets/   화면
assets/table.js       CSV에서 필요한 열만 읽기
assets/worker.js      Pyodide(웹어셈블리 파이썬)로 계산을 돌리는 워커
engine/recon3d.py     복원 프로그램
engine/thickness.py   호스 내경 추정
engine/template.html  결과 3D 화면
configs/              Run별 설정
```

웹 버전이 계산을 다시 구현한 것이 아니라 `engine/`의 파이썬 프로그램을 브라우저에서 그대로 실행합니다. 그래서 프로그램을 고칠 때도 이 파일들만 고치면 됩니다.

맞춤은 앞머리가 상자를 지나는 구간만 씁니다. 신호가 뚜렷해지는 시각을 잡고 곧은 경로로 속도를 대략 구해서 구간을 정합니다. 실측 Run #40에서 분석 구간 전체로 맞추면 평균 경로 오차가 0.58 cm이고 이 구간으로 맞추면 0.33 cm입니다.

맞춤은 세 단계입니다.

1. 호스와 시간을 성기게 자른 모델로 시작점마다 8걸음만 맞춥니다. 시작점은 6개, 갈래가 있는 구조는 12개입니다 (`starts`, `nfev1`).
2. 후보마다 잘 맞은 3개를 같은 모델로 수렴시킵니다 (`keep`, `nfev2`).
3. 앞선 후보의 답 2개를 원래 해상도로 마무리합니다 (`near`, `polish`, `nfev3`).

계산 조각은 입력과 출력이 숫자뿐이라 워커 수와 상관없이 답이 같습니다.

호스를 일정한 간격의 점으로 나눌 때 점 수는 정수입니다. 예전에는 점 하나의 호스 길이를 설정값으로 고정해서, 경로 길이가 바뀌어 점 수가 하나 늘 때마다 전체 신호가 약 2.4% 튀었습니다. 이제는 점 하나의 길이를 실제 간격으로 계산합니다. 굵기 바뀌는 점 P도 걸친 조각에서 앞뒤 값을 나눠 갖습니다. 그래서 목표 함수가 매끈해져서 시작점이 적어도 같은 답에 도달합니다.

Pyodide는 jsDelivr에서 불러오므로 학교 망에서 `cdn.jsdelivr.net`이 막혀 있으면 계산이 시작되지 않습니다. 버전은 `assets/worker.js` 맨 위에 고정되어 있습니다.

### 파이썬 결과와 비교

같은 설정과 데이터로 일반 파이썬(numpy 2.5, scipy 1.18)과 이 페이지(Pyodide 314.0.7)를 비교했습니다.

| | 일반 파이썬 | 웹 페이지 |
| --- | --- | --- |
| Run #40 χ²/N | 1.332 | 1.332 |

| Run #49 χ²/N | 1.717 | 1.717 |
| Run #49 실제 경로로 맞출 때 χ²/N | 2.013 | 2.013 |

Run #40은 저장되는 값이 0.0001% 이내로 같습니다. Run #49는 중간점이 0.01 cm 이내로 같습니다. 신호가 약해 값이 거의 정해지지 않는 차순위 답과 판정 불가 구간의 속도는 더 달라질 수 있습니다. 부동소수점 계산 라이브러리가 달라서 생기는 차이입니다.
